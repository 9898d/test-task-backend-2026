# Тестовое задание: ускорение ночной синхронизации

## Что было дорого

- **N+1 запросов**: на каждую сущность — отдельный `SELECT` по JSONB `@>` без индекса, `UPDATE jsonb_set` (перезапись всего документа), `COMMIT` (fsync WAL). На 20k+50k — ~70 000 SELECT + ~70 000 UPDATE + ~70 000 commit.
- **`update_jsonb_field`**: сырой SQL на каждое обновление JSONB-поля.
- **Чтение всей таблицы в конце** + `commit` внутри цикла по сущностям.
- **Баги**: `KeyError` в `filter_merge_abstract_customer` (перезапись списка внутри цикла по нему).

## Что изменено

- **Один SELECT** всех `AbstractCustomer` + **in-memory индексы** (`InMemoryIndex`):
  - `by_customer_crm_id`, `by_customer_login` (покупатели);
  - `by_lead_crm_id`, `by_lead_login` (сделки).
  - Направление поиска соответствует бизнес-правилам: покупатель ищется по id в CRM, иначе по логину среди **сделок**; сделка — по id в CRM, иначе по логину среди **покупателей**.
- **Применение в памяти**, один `flush()` + один `commit()` в конце (вместо 70 000 commit'ов).
- **Слияние**: `merge_into` + `index.reindex(by_crm)` **до** `remove_from_indexes(by_login)` — перенесённые записи остаются в индексе, указывая на `by_crm`. Если `by_login` — новый (pending insert), вызывается `session.expunge(by_login)`, чтобы flush не вставил дубль.
- **Смена логина** у существующего покупателя/сделки чистит старый логин из индексов.
- **Чистка вложенных сущностей** (`cleanup_entity`): удаляются `amo_customers`/`amo_leads`/`amo_contacts`/`amo_companies`, которых не было в выгрузке, и те, у кого в `name` есть «удалить» (регистронезависимо). Поведение как в исходном коде (контакты/компании не заполняются в этой выгрузке, поэтому старые удаляются).
- **Удаление `AbstractCustomer`**: одним `DELETE ... WHERE id NOT IN (...)` после успешного сбора. Для 20k+50k параметров много; альтернатива — `= ANY(:array)` или temp table (см. «Что можно улучшить»).
- **Безопасность**: весь сбор в `try/except` с `session.rollback()`. Если сбор прервался — удаление не запускается, частичные изменения откатываются.
- **Индексы**: GIN с `jsonb_path_ops` на 4 JSONB-поля + expression-индексы на `(amo_customers -> 0 -> 'general' ->> 'login')` / `... ->> 'name'` (аналогично для `amo_leads`) для внешнего поиска по точному логину/названию.

## Что оставлено и почему

- **JSONB-схема** — совместима с другими частями системы. README задания разрешает сохранить формат JSON.
- **`update_jsonb_field`** — оставлен для обратной совместимости (другие части системы могут его использовать). В ночном прогоне **не используется**.
- **`dict_compare_merge`** — оставлен, защищён от `KeyError` (записи без `general.id` пропускаются). Поверхностный `update`: более свежие данные побеждают.
- **`amocrm.py`** — не менялся по сути (кроме `as_dict()` и стаба `get_schema`), клиент CRM вне зоны задачи. В реальном клиенте `get_schema` переопределит стаб.
- **ORM-flush вместо батчевого `ON CONFLICT`** — осознанный выбор: `flush` в одной транзакции даёт **0.50 сек** на 2k+5k, что приемлемо для ночного прогона. Батчевый upsert через `execute_values`/`COPY` усложнил бы код и повысил риск багов с JSONB; выигрыш (~0.3 сек на 2k+5k, ~2–3 сек на 20k+50k) не оправдывает риск. Если понадобится — можно добавить позже, вынеся `INSERT ... ON CONFLICT (id) DO UPDATE` в отдельную функцию.

## Оценка памяти (20 000 покупателей + 50 000 сделок)

- **`existing`** — все загруженные `AbstractCustomer` с JSONB-полями. Если `api_value` в среднем 5–20 КБ, то `existing` занимает **~0.5–2 ГБ** (Python-оверхед dict/list/str ~2–5× от размера JSON).
- **Индексы** (`by_customer_crm_id`, `by_customer_login`, `by_lead_crm_id`, `by_lead_login`) — десятки МБ (70k ключей).
- **`new_objects`**, `customer_ids`/`lead_ids`/`contact_ids`/`company_ids` — единицы МБ.
- **Итого: 0.5–2 ГБ** в зависимости от размера `api_value`.

**Замер на бенчмарке (2k+5k, мок с пустым `api_value`):** `tracemalloc` peak ≈ **21 МБ** (с нуля) / **27 МБ** (повторно). Экстраполяция на 20k+50k (в 10 раз больше данных): ~**210–270 МБ** при пустом `api_value`. На реальных данных `api_value` 5–20 КБ → оценка **0.5–2 ГБ** выше.

**Что можно улучшить:** `load_only` на нужные поля (без `api_value`), если `api_value` не нужен для логики. Или вынести `api_value` в отдельную таблицу/колонку.

## Оценка числа запросов к Postgres

| Этап | Запросов |
|---|---|
| Загрузка существующих | 1 × SELECT |
| Flush (INSERT/UPDATE) | INSERT батчится через `insertmanyvalues` — ~70 statement'ов на 70k записей (батчи по ~1000). UPDATE — по одному на объект: ~70 000 statement'ов, если все старые и изменились. |
| Чистка вложенных (в памяти) | 0 |
| Удаление `AbstractCustomer` | 1 × DELETE (`NOT IN` с 20k параметров — ок для PG, но лучше `= ANY(:array)`) |
| Commit | 1 × COMMIT |
| **Итого** | **1 SELECT + ~70 INSERT (батчами) + ~70 000 UPDATE (если старые) + 1 DELETE + 1 COMMIT** |

**Ускорение** достигается за счёт устранения 70 000 commit'ов (каждый — `fsync` WAL) и 70 000 SELECT'ов (N+1). Если все объекты новые — INSERT батчится в ~70 statement'ов, а не 70 000. Если все старые и изменились — UPDATE остаётся 70 000 statement'ов (можно улучшить батчевым upsert, см. ниже).

**Что можно улучшить дальше:** батчевый upsert через `INSERT ... ON CONFLICT (id) DO UPDATE` или `psycopg.execute_values` — один statement на батч из 500–1000 → ~70–140 statement'ов вместо 70 000. В текущей реализации не сделано (см. «Что оставлено и почему»).

**«До» — исходный код + исходный мок-генератор (без уникальных логинов):**

| Метрика | Значение |
|---|---|
| Время | 74.00 сек |
| SELECT | 29 159 |
| INSERT | 3 503 |
| UPDATE | 10 153 |
| DELETE | 1 |
| Всего записей | 3 503 |

**«После» — оптимизированный код + `random.seed(42)`:**

| Метрика | С нуля | Повторно |
|---|---|---|
| Время (без `tracemalloc`) | **~0.50 сек** | **~0.28 сек** |
| Время (с `tracemalloc`) | ~2.92 сек | ~1.05 сек |
| SELECT | **1** | **1** |
| INSERT | **~4** (батчами, `insertmanyvalues`) | **0** |
| UPDATE | **0** | **0** |
| DELETE | 1 | 1 |
| Всего записей | **~3 489** | **~3 489** |
| Память peak (`tracemalloc`) | ~21 МБ | ~27 МБ |

**Ускорение: ~148x** (74 / 0.50, порядковое; см. примечание).

**Примечание про сопоставимость:** «До» замерялся на исходном коде с исходным мок-генератором (без уникальных логинов, с WARNING'ами). «После» — на оптимизированном коде с `random.seed(42)` и уникальными логинами (`cust_{i}`, `lead_{i}`). Количество записей различается (3503 vs 3489), потому что исходный генератор создавал другие комбинации логинов. **Сравнение порядковое**; для честного парного сравнения нужно перезапустить исходный код на новых данных (не входит в текущий репозиторий). Ускорение достигается за счёт устранения 70 000 commit'ов и 70 000 SELECT'ов, а не за счёт меньшего объёма данных.

**Про `INSERT=4`:** SQLAlchemy 2.x батчит INSERT через `insertmanyvalues` — 4 statement'а на ~3489 записей (батчи по ~1000), а не 3489 отдельных INSERT'ов. `UPDATE` не батчится (unit of work генерирует по одному на объект), но на первом прогоне новых объектов нет старых, поэтому `UPDATE=0`.

**Идемпотентность:** повторный запуск без очистки не создаёт дубликатов (`INSERT=0`), количество записей не меняется (`~3489`). Логины в мок-данных уникальны, seed фиксирован. Подтверждено строго.

**Сценарий слияния:** покрыт отдельным тестом `scripts/test_merge.py` (запуск: `python -m scripts.test_merge`). Проверяет, что `merge_into(ac1, ac2)` + `index.reindex(ac1)` + `remove_from_indexes(ac2)` + `session.expunge(ac2)` (для новых) корректно сливают две записи: остаётся 1 `AbstractCustomer` с логинами `cust_0`, `cust_1` и сделкой `100000`. **Тест пройден.** Это проверяет исправление багов «слияние ломает индексы» и «новый объект при слиянии даёт дубль».

## Ограничения и риски

- **Транзакция на весь прогон.** При сбое на 70-тысячной сделке — полный откат, повторный запуск с нуля. Для ночной синхронизации это консервативный и правильный выбор (лучше, чем частичные данные), но требует явного упоминания.
- **Expression-индексы работают только для первого элемента массива** `amo_customers`/`amo_leads`. Если у покупателя несколько CRM-покупателей, логины второго и далее не проиндексированы expression-индексом. Для полноценного поиска по всем элементам — GIN `@>` (он есть), но он для containment с точным путём, а не для `->>`. В README задания не оговорено иное; для «внешнего поиска по точному логину» обычно достаточно первого.
- **Контакты/компании в этой выгрузке не заполняются** (`amo_contacts`/`amo_companies` не пишутся в `get_customer_json`/`get_lead_json`). `cleanup_entity` чистит их по `contact_ids`/`company_ids` из `_embedded`; если в БД лежат старые контакты/компании с другими `general.id` — они будут удалены (что соответствует правилу «которых не было в выгрузке»). Поведение как в исходном коде.
- **`config.py`** содержит креды в дефолте для удобства локального запуска. В продакшене — только через `DATABASE_URL`.
- **`reindex(by_crm)` дублирует работу** `_index_customer`/`_index_lead` для уже проиндексированных записей `by_crm`. При большом числе слияний это O(размер `by_crm`) на каждое. На реальных данных слияний меньше; не критично для 20k.

## Как запустить

1. Настроить `config.py` (PostgreSQL) или задать `DATABASE_URL`.
2. `pip install -r requirements.txt`
3. `python -m scripts.benchmark`

Бенчмарк использует мок-генератор `scripts/mock_data.py` и подменяет `amocrm_get` через `unittest.mock.patch` (клиента CRM в репозитории нет).

**Проверка идемпотентности:** закомментируйте 2 строки очистки в `benchmark.py` (`db.session.query(...).delete()` и `ALTER SEQUENCE ...`) и запустите повторно — ожидается `INSERT=0, UPDATE=0`, количество записей не меняется.

**Проверка слияния:** `python -m scripts.test_merge` — ожидается `ТЕСТ СЛИЯНИЯ ПРОЙДЕН` (1 `AbstractCustomer`, логины `{cust_0, cust_1}`, сделка `100000`).
